# Features Collection - Standard Schema

## Collection Path
```
/features
```

## Document Structure

Every feature document should have the following fields:

### Required Fields

```json
{
  "id": "puzzles",                          // REQUIRED: Unique ID (ALWAYS lowercase)
  "name": "puzzles",                        // REQUIRED: Feature name (ALWAYS lowercase)
  "label": "Puzzles",                       // UI label (can be mixed case)
  "displayName": "Puzzles",                 // Display name for UI (can be mixed case)
  "description": "Think, match, spot...",   // Feature description
  "icon": "🧩",                              // Emoji icon for UI
  "featureType": "puzzle",                  // Type: "puzzle", "quiz", "story", "game"
  "type": "puzzle",                         // Same as featureType (for compatibility)
  "enabled": true,                          // Boolean: is feature enabled
  "isPublished": true,                      // Boolean: is feature published
  "order": 2,                               // Number: sort order (0-999)
  "createdAt": "2025-12-24T11:24:06.942Z", // Timestamp: when created
  "updatedAt": "2025-12-27T02:29:00.000Z"  // Timestamp: when last updated
}
```

## Critical Rules

### 1. Document ID vs `id` Field
```
✅ CORRECT:
   Document ID: <auto-generated by Firestore>
   id field: "puzzles"

❌ WRONG:
   Document ID: "Puzzles"
   id field: <missing>
```

### 2. Lowercase Rule
```
✅ CORRECT:
   id: "puzzles"
   name: "puzzles"

❌ WRONG:
   id: "Puzzles"
   name: "Puzzles"
```

### 3. Label vs Name
```
✅ CORRECT:
   name: "puzzles"     (lowercase - used in queries)
   label: "Puzzles"    (mixed case - used in UI)

❌ WRONG:
   Both lowercase or both mixed case
```

## Validation Checklist

Before deploying to production, verify each feature document:

- [ ] Has `id` field (NOT document ID)
- [ ] `id` field is ALL lowercase
- [ ] `name` field is ALL lowercase
- [ ] `name` === `id` (exact match)
- [ ] Has `label` field
- [ ] Has `displayName` field
- [ ] Has `featureType` field
- [ ] Has `type` field (same as featureType)
- [ ] Has `enabled` field (boolean)
- [ ] Has `isPublished` field (boolean)
- [ ] Has `order` field (number 0-999)
- [ ] Has `createdAt` timestamp
- [ ] Has `updatedAt` timestamp
- [ ] Has `description` field
- [ ] Has `icon` field (emoji)
- [ ] NO deprecated fields: `status`, `featureName`

## Common Issues & Fixes

### Issue 1: Categories Don't Load
**Cause**: Feature `id` field is wrong or missing
**Fix**: 
1. Ensure `id` field exists
2. Ensure `id` is lowercase
3. Ensure categories have matching `featureId`

### Issue 2: Feature Updates Fail
**Cause**: Document doesn't exist (wrong ID)
**Fix**: Use `setDoc` with `merge: true` instead of `updateDoc`

### Issue 3: Feature Appears Duplicate
**Cause**: Document ID and `id` field don't match
**Fix**: Delete old document, keep only correctly-named document

### Issue 4: Queries Return No Results
**Cause**: Field names don't match query expectations
**Fix**: Ensure all required fields are present with exact names

## Migration Path

If you have legacy features with wrong structure:

1. **Do not delete** old documents
2. **Create new documents** with correct structure
3. **Redirect queries** to new document IDs
4. **Test thoroughly** before deleting old documents
5. **Archive old documents** in a backup collection first

```

```

## Automatic Normalization

The `NormalizeFeatures` utility (`/admin/normalize-features`) automatically:

1. ✅ Creates missing `id` fields
2. ✅ Converts all `id` to lowercase
3. ✅ Converts all `name` to lowercase
4. ✅ Adds missing `order` fields
5. ✅ Adds missing timestamps
6. ✅ Removes deprecated fields
7. ✅ Creates new documents with correct IDs
8. ✅ Deletes old documents with wrong IDs
9. ✅ Preserves all other data

**Run this tool if you've edited features manually or had data migrations.**
